1. blocking Resolver (steps 1-2) and Testing bullet 1: "a triple never mixes sources" is false. A flag or env layer that sets only some directories fills the rest from layer-4 defaults, not from the active business. `COS_PROJECTS=/p cos brief` with active `acme` yields home = build clone, workspace = build clone, projects = /p, which is the partial-edit mix the Problem section names. The test "COS_HOME with an active business gives the env triple" asserts the mixed result, and no test asserts no-mix. Evidence: main.rs:18 (`COS_HOME`, default `default_home()`), main.rs:22 (`COS_WORKSPACE`), main.rs:25 (`COS_PROJECTS`, default `$HOME/Projects`), main.rs:41-44 (`ws()` falls back to home); design Resolver steps 1-2 ("each missing directory from the defaults"). Fix: pick one rule and state it in Decisions: (a) a partial flag or env layer is an error naming the directories it does not set whenever a registry business would otherwise apply, or (b) missing directories come from that business. Record the per-directory source in `Triple`. Add a test that, for `COS_PROJECTS` alone with an active business, asserts the chosen rule for CLI and app.

2. blocking Long-lived processes and launchd, Acceptance 8: the design drops `COS_HOME` from the plist environment but not from the log paths, which still read `@COS_HOME@`. Taskfile fills that placeholder from ROOT_DIR, so the logs stay on the install home for any business. The design says logs go to "the resolved home's out/logs, which the job creates", but launchd opens StandardOutPath/StandardErrorPath before the process starts, so the job cannot create its own log directory. Acceptance 8 has no `out/logs` precondition. Also `--business @BUSINESS@` "and nothing otherwise" cannot be produced by a sed substitution (`sed -e ... -e ...` in Taskfile.yml:194) without two templates or a generated argument list. Evidence: launchd/cos.brief.plist:24-25 and launchd/cos.dash.plist:20-21 (`@COS_HOME@/out/logs/*`); Taskfile.yml:194; design Acceptance 8. Fix: `task schedule BUSINESS=<name>` creates `<that business's home>/out/logs` before `launchctl bootstrap`; state the log location when no BUSINESS is given (the install home, since the active business is not known at schedule time); name how the optional `--business` argument is emitted; add the `out/logs` creation to the Acceptance 8 preconditions. Unverified here: launchd behaviour with a missing log directory (no run performed).

3. blocking Semantic ISA, side-effect inventory and sinks: two process-executing or repo-mutating side effects are missing. (a) `agents_rejudge` runs every contract check as `sh -c <cmd>` in `spec.workdir`: judge runs the checks once status is Done, and rejudge calls judge. (b) `agents_clean` runs `git worktree remove --force` against `spec.repo`, read from the run's `spec.json`, after `read` (which reconciles). The inventory row for rejudge lists only writes, and the clean row says "files, no" without a sink or VERIFY. The Sources list (CLI args, picker name, registry, settings.json, COS_* env) omits the run records (`spec.json` and `state.json` under the switched home), and `spec.json` holds commands from the Hire dialog's contract. Evidence: src/agents/judge.rs:281-301 (`Command::new("sh").arg("-c")`, `current_dir(workdir)`), judge.rs:139-141 (checks run when `Status::Done`); src/agents/mod.rs:498-504 (rejudge calls judge), mod.rs:418 (spec.json written from the request), mod.rs:595-604 (`git worktree remove --force` on `spec.repo`). Fix: add a row for each execution with its VERIFY (workdir resolves under the active home's `out/agents`; the repo path is one the run was hired on, or the call is refused and nothing runs); add run records to Sources with their check; add an ISA test: rejudge after a switch runs checks only under the new home's worktree, and clean with a `spec.repo` outside the projects directory is refused.

4. should Desktop, First-run migration: the CLI and the app each migrate and can pick different `default` triples. The CLI migrates from resolver layers 1, 2 and 4 and never reads the legacy `settings.json` directories (settings.rs:44-58 is the only reader). Whichever binary runs first while no registry exists decides. A `cos business list` run first writes the CLI triple, and the app's legacy workspace, the only app switch today, is never read again. A `COS_HOME` or `COS_PROJECTS` exported on the first run becomes permanent in `default`. The app also migrates without the env layer but resolves with it, so `default` and the pinned app triple can differ. Evidence: design First-run migration ("from resolver layers 1, 2 or 4"; "the app from its legacy settings.json directories if present, else layer 4"); apps/desktop/src/settings.rs:44-58; apps/desktop/src/lib.rs:59-80. Fix: migrate from non-env sources only, in both binaries (legacy `settings.json` if present, else defaults), so the persisted `default` never depends on the first command's environment. Also state that the CLI refuses to create the registry while `settings.json` holds legacy directories and names `cos` app start as the migration path, or define the one path that writes it.

5. should Desktop, startup: a corrupt or dangling registry at app start is undefined. The ISA violation row says "commands that resolve stop", but app startup resolves before any command, and the design says nothing about the window. The current code drops an unparseable `settings.json` silently (settings.rs:45-47); the design says the new one is reported in the header, but the registry gets no equivalent. Evidence: design ISA "Violations" row "registry unparseable, bad name, dangling active"; design Desktop ("At start the app runs first-run migration if needed, then resolves"); settings.rs:45-47. Fix: on a registry error the app starts on defaults with a header error naming file and key, and `switch_business` is refused until the file is fixed.

6. should Desktop, reload and hash restore: restoring `#tab=docs` after `location.reload()` leaves the Docs room blank. The docs and flows frames load only inside the tab click handler, and `showPane` is not a tab click. Evidence: apps/desktop/ui/app.js:134-152 (frame `src` set only on click for docs and flows), app.js:195-202 (`showPane`), design Desktop ("`app.js` reads that hash at startup and opens the same tab and pane"). Fix: restore by dispatching the same click on `.app-tab[data-view=<tab>]`, then call `showPane` for the agents pane; add to the hand-check: switch while on Docs, confirm the room shows the new business.

9. should Testing, spawn: "spawn with `COS_BUSINESS` or `COS_WORKSPACE` set in the parent reaches `running`" passes whether or not the env is removed, because it asserts nothing about the child's triple. 10. should Desktop, spawn env and harness: the design removes `COS_*` from the supervisor's env, but the harness inherits the supervisor env (supervise.rs:165 sets only `PATH`). If the harness runs `cos` (not verified here), that call resolves through the registry's active business, not the run's business. Evidence: src/agents/supervise.rs:165; design Desktop (spawn bullet). Fix: state whether a harness may call `cos`; if it may, the supervisor passes the run's triple to the harness env explicitly, and the ISA matrix gets a row for it.

11. should Desktop, `businesses()`: one unreadable record breaks the whole picker. `agents::list` collects `read` for every id with `?`, and `read` fails on a bad `spec.json`, so a single bad run in one business fails the list. A moved or unmounted business directory is also an error, and the design sets no per-business error rule. Evidence: src/agents/mod.rs:446-449 (`read`, `spec.json` with `?`), mod.rs:455-465 (`list` collects with `?`); design Desktop (`businesses()` bullet). Fix: `count` returns an error per business, skips unreadable records, and the picker row shows the error. Test: a corrupt `spec.json` in one business leaves the other rows counted.
